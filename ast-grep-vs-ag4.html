ast-grep と ag4 の差異

本家 @ast-grep/cli@0.51.0 と ag4 を、固定コーパス・同一パターンで比較した 2026-10-25 時点の要約です。既定バックエンドは tree-sitter（C# 含む）。 ANTLR / Roslyn は切替時の数値です。

いまの位置づけ: Java / C++ / Python / C# の既定は tree-sitter。説明不能差分は known-differences.yml 適用後に 0。本家とヒット集合を 100% 揃えることは目標にしない。ag4 の強みは .NET 組み込み・NativeAOT DLL・ANTLR .g4（本家に無い言語含む）にある。

1. 比較の前提

  • ハーネス: tools/AstGrepAntlr.DiffTest
  • 対象言語: Java / C++ / C# / Python（PL/SQL は本家に言語が無く表では —）
  • コーパス: commons-lang、java-design-patterns、google-java-format、leveldb、cereal、fmt、 Newtonsoft.Json、Humanizer、serilog、click、attrs、flask（tag / SHA 固定）
  • パターン: 呼び出し・$$$・文・複合ルール・rewrite など各言語数十件
  • 詳細表: difftest/REPORT.md
ag4 の言語: Java / C++ / Python / C# = tree-sitter 既定。Java / C++ / Python は --backend antlr、C# は --backend roslyn。PL/SQL・SQLite は ANTLR。 独自 DSL は sgconfig.yml の customLanguages（.g4 / .interp）。

4. パース性能の現状

ボトルネックはマッチではなくパース。詳細は speedupissue.md。

対象 parse 要点
Java · tree-sitter（commons-lang 264） ~0.67s native ≈ arena 変換。エラー無しファイルの diag 走査はほぼ 0
Java · ANTLR（同） ~3.3s LL フォールバック 67%（177/264）。SLL 失敗後の全文 LL やり直し
C# · tree-sitter（corpus 1587） ~4.4s cursor 走査 + 軽い P/Invoke。マッチは全体の数％
C++ · ANTLR（leveldb 80） ~13s LL フォールバック 75%。difftest が桁違いに遅い主因

起動（10 回平均、win-x64）: NativeAOT ≈ 42ms、dotnet ag4.dll（JIT）≈ 254ms。 リリース exe は AOT。言語は遅延登録。ANTLR の DFA を温めるなら DLL / NuGet / MCP を推奨。

LL フォールバックの大半は「構文エラーの回復」ではなく、正しい入力でも SLL 予測が足りず LL に落ちるケース。削減の本命は文法側の曖昧さ低減。

5. 用途の目安

用途 向き
本家と同じ感覚の検索（Java / C++ / Python / C#） 本家、または ag4（tree-sitter 既定）
ANTLR 文法・独自 DSL・本家に無い言語（PL/SQL、SQLite など） ag4（ANTLR / .g4）
.NET プロセス内・NativeAOT DLL・MCP ag4
C# で Roslyn CST が欲しいとき ag4 --backend roslyn（本家との一致率は下がる）

6. 残る差の典型

tree-sitter 既定でも残る照合差

  • 単一子 unwrap・modifier 読み飛ばし・extra（コメント等）の扱い
  • ag4 の MetaVarVariants によるプレースホルダ展開
  • 同じヒットでもメタ変数のキャプチャ範囲がずれる場合（特に C#）

ANTLR 切替時

  • ag4 が広い 呼び出しパターンがコンストラクタ / this / super まで拾いやすい
  • 本家が広い 複雑なメソッド宣言・現代 C++ / Python インデントなど、文法限界で取りこぼし

Roslyn 切替時（C#）

  • 括弧付き式とキャスト、identifier の粒度、ブロック括弧の形
  • 本家（tree-sitter-c-sharp）との CST 差が一致率約 53% の主因
