ast-grep と ag4 の差異

本家 @ast-grep/cli@0.51.0（tree-sitter）と ag4（既定は Java / C++ / Python も tree-sitter、切替で ANTLR）を、実コーパス上で同じパターンで比較した結果の要約です。エンジン不具合ではなく「構文木・照合ロジックの違い」として扱う差分を中心にまとめています。

方針: 文字コード・終了コード・byteOffset・パターンコンパイル失敗など ag4 側の不具合は修正済み。ag4 は Java / C++ / Python で tree-sitter を既定にできるため、本家との kind 差は縮小します。残差は主に照合（unwrap・modifier 読み飛ばし・MetaVarVariants など）と C#（Roslyn）です。--backend antlr 時の木のズレは difftest/known-differences.yml （任意の backend: フィールド）に理由付きで記録します。本家と 100% 同じヒット集合は目標にしない。

1. 比較の前提

  • ハーネス: tools/AstGrepAntlr.DiffTest
  • 本ページの数値比較対象: Java / C++ / C# / Python（本家に対応言語があり、固定コーパスで 差分計測しているもの）。PL/SQL は本家に言語が無いため表では「—（本家なし）」
  • コーパス: commons-lang / java-design-patterns / leveldb / cereal / fmt / Newtonsoft.Json / Humanizer / click / attrs（tag・SHA 固定）
  • パターン: 呼び出し・$$$・文・複合ルール（kind なし）・rewrite など各言語約 55 件
  • 詳細レポート: difftest/REPORT.md
ag4 組み込み言語（現時点）: Java / C++ / Python（tree-sitter 既定、ANTLR 切替可）、C#（Roslyn）、PL/SQL・SQLite（ANTLR）。 加えて sgconfig.yml の customLanguages（.g4 / .interp）で独自 DSL も可。差分テストは --backend で両方計測できます。

3. 精度をどう見るか

ast-grep の主目的は「パターンどおりの構文を、意図どおりに拾う／書き換える」ことです。そのときの正解の基準は、事実上 tree-sitter 上のパターン意味です。

用途 どちらが向くか
本家と同じ感覚の検索・ルール（Java / C++ / Python、tree-sitter 既定） 本家 ast-grep または ag4（tree-sitter）（kind は揃うが照合差は残る）
ANTLR 文法・独自 DSL・本家に無い言語（例: PL/SQL、SQLite、カスタム .g4） ag4
C#（Roslyn CST） ag4（Roslyn）／本家（tree-sitter-c-sharp）— 別名で一部吸収
.g4 を拡張すればパースできる構文は増える（特に C++）。ただし同じソースでも木の切り方が違う限り、ヒット集合やメタ変数の完全一致には至らない。マクロ前処理も g4 だけではコンパイラ並みにはならない。

4. 典型的な差異（具体例）

tree-sitter 既定で解消・軽減しやすいもの

  • kind 名の不一致（例 methodDeclaration → method_declaration）
  • C++ の現代構文・Python のインデントブロックなど、ANTLR 文法限界による取りこぼし

ANTLR を選んだときに残る差（下表・例は ANTLR ベースライン）

ag4 が広い $F($$$ARGS) の取りすぎ

意図（本家寄り）は「普通のメソッド呼び出し」。ag4 は呼び出しに見える／似た形を広く拾いやすい。 

foo(1, 2);      // 両方ヒットしやすい
obj.bar(x);

new Foo(1, 2);  // コンストラクタっぽい木 → ag4 が拾いやすい
this(1);        // 明示 this
super(x);       // 明示 super

difftest の call-any（commons-lang）では same ≈ 1 957 に対し only-ag4 ≈ 6 293。

本家が広い public $TYPE $NAME($$$PARAMS) { $$$BODY } の取りこぼし

意図は本体付き public メソッド全般。ag4 はシンプルな形以外で外れやすい。

public int run(int x) { return x; }   // 両方ヒットしやすい

public void run() { }                 // void が $TYPE に乗りにくい
public <T> T id(T x) { return x; }  // 型パラメータ
public int f() throws IOException { return 0; }
@Override
public String toString() { return ""; }

difftest の public-method では same ≈ 290 に対し only-ast-grep ≈ 1 450（ag4 の取りこぼし）。

その他のよくあるズレ（ANTLR / Roslyn）

  • Java・本家のみ（ANTLR）: import / package の分割、アノテーション、multi-catch / try-with-resources、diamond・匿名クラスの new、一部の if ブロック
  • Java・ag4 のみ（ANTLR）: this/super 呼び出し、lambda / method-ref、一部 for / class-body
  • C++・本家のみ（ANTLR）: 現代構文・マクロで CPP14 が弱い（一致率低下の主因）
  • C#・本家のみ: 括弧付き式をキャストとみなすケース、 identifier の粒度差、await / lambda / typeof・nameof など
  • C#・ag4 のみ: 中括弧付き if/for/while/foreach、 public $T $N(...) など Roslyn では当たりやすいパターン

tree-sitter でも残る差（照合ロジック）

  • 単一子の unwrap・modifier の読み飛ばし・extra（コメント等）の扱い
  • MetaVarVariants など ag4 独自のプレースホルダ展開
  • 同じヒットでもメタ変数のキャプチャ範囲がずれる場合

5. 揃えた／近づけた点（差異ではない）

  • 終了コード（run 0/1/2、scan の --error-on）
  • 文字コード・BOM 保持、--encoding
  • JSON の 0-based 行・列、実ファイルの byteOffset
  • stopBy 既定 neighbor、precedes/follows
  • gitignore・globs・隠しファイル扱い
  • 文パターン（if / for / try など）のコンパイル失敗の解消
  • kind 名が本家と同じ（Java / C++ / Python の tree-sitter 既定）
  • --backend / languageBackends による ANTLR 切替
